# Code-Explainer Recovery Plan

Date: 2026-03-02
Owner: Anshumani Ruddra / maintainers

## Goal

Make `code-explainer` reliably useful for PMs, designers, and new engineers by producing high-signal, human-readable onboarding explainers and diagrams, not just structural summaries.

## Success Criteria

1. A non-technical reviewer can answer in <10 minutes:
1. What this repository does.
2. Who uses it.
3. Where primary user/request flow starts and ends.
4. Which 3-7 directories/modules matter most.
2. `OVERVIEW.md` and `html/ONBOARDING.html` are both generated by default.
3. LLM behavior is explicit (`auto|required|off`) and enforceable.
4. Generic placeholder output is surfaced by quality gates.

## Milestones

### Phase 1: Contract and Defaults

Deliverables:
1. New LLM contract: `--llm-mode auto|required|off`.
2. Backward compatibility for `--enable-llm-descriptions`.
3. Default output format changed to `both` (markdown + html).
4. Manifest and quality reports include `llm_mode`.

Acceptance tests:
1. Run with defaults produces both markdown and html artifacts.
2. Run with `--llm-mode off` never attempts LLM calls.
3. Run with `--llm-mode required` fails quality gate if LLM is not used.

### Phase 2: Explainability Upgrade (No-LLM and LLM)

Deliverables:
1. Richer fallback summary when LLM unavailable (not generic placeholders).
2. Role-based directory/module descriptions from file signals.
3. HTML summary fallback mirrors markdown quality.

Acceptance tests:
1. `OVERVIEW.md` contains concrete repo facts (language, modules, entrypoints, flow).
2. Directory map has role-based lines, not repeated "Module with N files".
3. HTML hero summary includes flow + architecture context.

### Phase 3: Semantic Quality Gates

Deliverables:
1. Warn/error on placeholder-heavy onboarding content.
2. Enforce LLM-required runs.
3. Keep structural checks and fact-check checks.

Acceptance tests:
1. Placeholder-heavy overview triggers warnings.
2. `llm_mode=required` + no key causes quality failure.
3. `llm_mode=auto` + no key warns but can still pass.

### Phase 4: Flow/Diagram Fidelity (Next Iteration)

Deliverables:
1. Better entrypoint and route extraction by framework.
2. More evidence-driven flow diagrams from resolved call/import chains.
3. Reduced fallback placeholders in deep-mode diagrams.

Acceptance tests:
1. At least one flow links real entrypoint -> service/domain -> data boundary.
2. Diagram labels reference actual modules/files where possible.
3. Deep mode outputs trust/data lineage that match dependency evidence.

### Phase 5: Benchmark and Publication

Deliverables:
1. Benchmark fixture set (small FE, backend API, monorepo, polyglot).
2. Rubric-scored output quality snapshots.
3. Release notes + migration docs for new flags/defaults.

Acceptance tests:
1. Benchmarks pass quality gate.
2. At least 80% rubric score for non-technical clarity on fixture set.
3. Documentation updated for install/run/default behavior.

## Risks

1. LLM dependency can make runs inconsistent.
Mitigation: deterministic fallback + explicit `llm_mode`.
2. Better prose may still drift into generic claims.
Mitigation: stricter semantic gates + evidence references.
3. Runtime may increase.
Mitigation: keep `quick|standard|deep` bounded behavior and limits.
